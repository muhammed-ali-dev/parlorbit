# Private alpha hosting

The deployment is one Go service serving the React build and APIs, one persistent SQLite disk, and an optional separately managed LiveKit project. The Render blueprint already uses /readyz and /var/data/roomcade.db. It remains a single-instance deployment.

## Configure and deploy

Connect this repository as a Render Blueprint and review its paid service and disk before deployment. Set DEMO_PASSWORD to a private value of at least 12 characters. Keep DEMO_PASSWORD_REQUIRED=true while the paid AI experiment is exposed. METRICS_TOKEN is generated by the blueprint. Keep these backend secrets out of frontend code and Git.

For calls, configure all three LIVEKIT_URL, LIVEKIT_API_KEY, and LIVEKIT_API_SECRET in the service environment. The hosted URL must use wss://. Add the service's HTTPS /api/v1/livekit/webhook URL to the LiveKit project using the corresponding signing credentials. Do not use the local devkey/secret values on the hosted service.

SECURE_COOKIES=true and the exact Render HTTPS origin are set by the blueprint. If adding a custom domain, include its exact HTTPS origin in ALLOWED_ORIGINS. Leave EMBEDDING_ENABLED=false until Codenames iframe availability and publisher permission are verified. The external-tab game flow works with the same shared lobby.

Render preserves only data beneath the disk mount. Its disk permits one service instance and can introduce deployment downtime. See [persistent disk documentation](https://render.com/docs/disks).

## Backup and restore

The deployment image includes /app/roomcade-db. It creates a new standalone SQLite snapshot using VACUUM INTO, verifies integrity, foreign keys, and application tables, and refuses to overwrite an existing file. Committed WAL data is included. See [SQLite snapshot semantics](https://www.sqlite.org/lang_vacuum.html).

Run in the service shell, choosing a new filename each time:

```sh
/app/roomcade-db backup -source /var/data/roomcade.db -output /var/data/alpha-backup-001.db
/app/roomcade-db verify -source /var/data/alpha-backup-001.db
```

Download the verified backup through the service's authenticated file-transfer access and keep an encrypted copy outside the service disk. Treat it as private data: it contains membership, names, invite hashes, sessions, and usage counters. A backup on the same disk alone is not disaster recovery. Backups are operator-run; no recurring job or off-site storage has been provisioned.

Exercise recovery first into a new database filename in a private environment:

```sh
go run ./cmd/roomcade-db verify -source /private/path/alpha-backup-001.db
cp -n /private/path/alpha-backup-001.db /private/path/restored-alpha.db
DATABASE_PATH=/private/path/restored-alpha.db ADDR=:8081 go run ./cmd/roomcade
```

Use a compatible application build, preserve the relevant signing configuration, and check House membership and shared game data. Existing guest cookies should still identify members when accessed on their original app origin. A separate origin will not inherit those cookies. Do not serve a restore drill publicly.

For actual recovery, stop the old service and verify a separately restored filename before changing DATABASE_PATH. Keep the original database and its WAL/SHM together for investigation; do not copy a live main database file alone. Take a verified backup before deployment or recovery changes.

## Acceptance before inviting groups

- /healthz returns 200; /readyz returns 200 only with database access and the frontend build.
- Use an authenticated metrics scrape to check /metrics; do not expose METRICS_TOKEN in URLs. Configure host error alerts and external availability monitoring.
- A friend enters a name, asks to join, closes/reopens the invite, and enters the room automatically after approval. Repeat with a physical phone.
- Test invalid/rotated invites, full Houses, expired/declined requests, and browser-cookie loss.
- Reload the host during a session and check reconnection; disconnect beyond the 30-second host recovery window and check host transfer.
- Verify audible speech/video between two physical devices on separate networks, mute, camera stop, room switching, and reconnection.
- Restart the service and confirm durable House/game data. Presence and arena state are transient.
- Save an off-disk verified backup and run a private restore drill.

Local evidence: browser tests cover direct approved-room entry and pending request recovery across tabs, host reload recovery, and host transfer after the grace period; media tests use simulated devices. Go tests restore a live WAL database into a separate file and preserve guest access, invites, and game data. Physical-device checks, hosted deploy, Docker image build, alerts, off-site storage, and recurring backups remain operational acceptance work.
